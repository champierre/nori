糊 nori
nori とは しくみ qpdf・lopdf との比較 インストール 使い方 GitHub
English

何千枚の PDF を、一枚に貼り合わせる。

nori は複数の PDF を 1 つにつなぐコマンドです。入力を 1 枚ずつ読み、そのページに要るものだけを出力に貼り足してから、次の 1 枚を開きます。だから、メモリ使用量は入力の数に関係なく、いちばん大きい入力 1 つ分にとどまります。

インストール GitHub でソースを見る
  • 6 MB2,000 ファイルをつないでも、メモリはこれだけ（3 種類の PDF で 5.4〜16 MB）
  • 16 倍qpdf より速い（Wikimedia Commons のランダムな 40 件を 1 回でつなぐ）
  • 1 つ外部コマンドに依存しない単体のバイナリ。MIT ライセンス

読んだそばから書き、捨てる

PDF の結合ツールの多くは、まず全部の入力を読み込み、1 つの文書にまとめてから、最後に書き出します。扱いやすい作りですが、メモリは入力の合計に比例して増えます。qpdf も、lopdf の README にある結合コードも、この形です。

nori は入力を 1 つ読むたびに、そのページと、ページが参照するもの（コンテンツストリーム、フォント、画像、注釈）だけを新しい番号で出力に書き足し、その入力を捨ててから次を開きます。ページツリーと相互参照表は最後に書きます。だから、メモリに載るのはいつも入力 1 つ分と、出力したオブジェクトの位置だけです。

全部読んでから書くメモリは入力の合計

  1. 入力を全部読む
  2. 1 つの文書にまとめる
  3. 書き出す

noriメモリは入力 1 つ分

  1. 1 つ読む
  2. ページに要るものを書く
  3. 捨てて次へ
  • ストリームには触りませんフォントや画像の中身は、展開も再圧縮もせず入力のまま書きます。速く、出力は qpdf とほぼ同じ大きさです。
  • ページに要るものだけしおりやフォーム、タグ付き PDF の構造ツリーは引き継ぎません。ページから参照をたどって届くものだけをコピーします。
  • 解析は先読みできます-j 6 のように指定すると、6 つの入力を別スレッドで同時に解析します。オブジェクトの多い入力では時間が半分になり、メモリは解析中の入力の分だけ増えます。

qpdf と lopdf との比較

Wikimedia Commons からランダムに選んだ PDF を 10〜2,000 個コピーしてつなぎ、qpdf と、lopdf の README にある結合コードとで、実行時間と最大メモリを比べました。いずれもコマンドとして実行した 5 回の中央値です。グラフの上のボタンで、入力の PDF を切り替えられます。

コピー元は、ランダムに取った 40 件の中から、作りの違う 3 件を選びました。どれもパブリックドメインか自由なライセンスで、リンク先からそのまま取得できます。

最大メモリ使用量

横軸はファイル数。nori の線は、入力が 200 倍になってもほとんど動きません。lopdf の線が途中で終わるのは、その先はメモリが計測機に収まらないためです。

  • オブジェクトの少ない PDF では、速さもメモリも桁が違います英国の法令を 2,000 ファイル（8,000 ページ）つなぐと、nori が 1.12 秒・5.7 MB、qpdf が 5.9 秒・423 MB、lopdf が 3.6 秒・695 MB でした。nori のメモリは 10 ファイルの 1.8 MB からほとんど増えていません。
  • オブジェクトの多い PDF でも、メモリは一定のままですEU 官報は 1 ファイル 478 オブジェクトあり、解析に時間がかかります。それでも nori は qpdf の 2.9 倍速く、-j6 なら 4.5 倍です。メモリは 2,000 ファイルで nori 16 MB、qpdf 2 GB でした。
  • スキャンした画像の PDF では、時間の差は縮まります新聞のスキャンは 1 ページ 9 オブジェクトしかなく、処理の大半が画像データの書き写しです。2,000 ファイル（1.2 GB）で nori 1.53 秒、qpdf 2.60 秒と差は 1.7 倍にとどまりますが、メモリは nori 5.4 MB、qpdf 57 MB、lopdf は 1,000 ファイルで 1.3 GB でした。
  • lopdf が遅いのではなく、結合コードの作りの問題ですnori 自身も入力の解析には lopdf を使っています。README の結合コードは全入力を 1 つの Document に集めて最後に保存するため、メモリが入力の合計に比例します。ページから参照されないオブジェクトも出力に残すので、出力が少し大きくなります。

計測方法

Mac（Intel Core i5-8500B 6 コア、メモリ 16 GB、macOS 15.8）で、nori 0.1.0、qpdf 12.4.2、lopdf 0.47.0 を比べました。伸び方の計測では入力を指定した数だけコピーし、各ツールをコマンドとして 1 回ウォームアップしてから 5 回実行し、時間とメモリ（最大常駐メモリ）を /usr/bin/time で取得しています。出力は qpdf でページ数と --check を確かめました。

nori -o output.pdf input-00001.pdf input-00002.pdf ...
nori -j 6 -o output.pdf input-00001.pdf input-00002.pdf ...

qpdf --warning-exit-0 --empty --pages input-00001.pdf input-00002.pdf ... -- output.pdf

lopdf-merge -o output.pdf input-00001.pdf input-00002.pdf ...

入力は Wikimedia Commons からランダムに選んだ PDF で、bench/fetch.py が一覧の作成と取得をします。lopdf は EU 官報で 100 ファイル、新聞のスキャンで 1,000 ファイルの時点でメモリが 400 MB〜1.3 GB に達したため、その先はこのマシンでは測っていません。計測スクリプトと入力の一覧は bench/ にあります。

コピーするもの、引き継がないもの

コピーするもの

  • ページと、その順序
  • コンテンツストリーム、リソース、フォント、画像
  • 注釈（ページを指す参照は出力のページに付け替えます）
  • ページツリーの途中で指定された MediaBox・CropBox・Resources・Rotate（各ページに書き込みます）

引き継がないもの

  • しおり（Outlines）とフォーム（AcroForm）
  • 名前付き宛先、タグ付き PDF の構造ツリー
  • 文書情報と XMP メタデータ
  • 存在しないオブジェクトへの参照（null になります）

インストール

Rust 1.88 以降の開発環境でソースからインストールします。できるのは nori という 1 つの実行ファイルで、qpdf などの外部コマンドには依存しません。

cargo install --git https://github.com/champierre/nori
nori --version

使い方

出力先と入力を並べるだけです。ページは入力の順につながります。

入力が 1 つでも読めなければ全体を失敗にし、出力ファイルは残しません。理由は標準エラー出力に nori: ... で出ます。

オプションと終了コードの一覧は nori --help で確認できます。

コマンドライン

# 3 つの PDF を順につなぐ
nori -o merged.pdf a.pdf b.pdf c.pdf

# 入力の一覧をファイルから読む（1 行 1 パス。- で標準入力）
ls pages/*.pdf | nori -o merged.pdf --list -

# 6 つの入力を同時に解析する
nori -j 6 -o merged.pdf --list inputs.txt

Rails から呼び出す

require "open3"

Dir.mktmpdir do |dir|
  inputs = pdfs.each_with_index.map do |pdf, i|
    File.join(dir, "#{i}.pdf").tap { |path| File.binwrite(path, pdf) }
  end
  output = File.join(dir, "merged.pdf")
  _out, err, status = Open3.capture3("nori", "-o", output, *inputs)
  raise "PDF の結合に失敗しました: #{err}" unless status.success?
  File.binread(output)
end
