Thousands of PDFs,pasted into one.

nori merges PDF files into one. It reads one input, pastes what its pages need onto the output, and only then opens the next. Memory use therefore stays around the size of the largest single input, however many files you merge.

Install Source on GitHub
  • 6 MBpeak memory for 2,000 files (5.4 to 16 MB across three kinds of PDF and two machines)
  • 16×faster than qpdf merging 40 random PDFs from Wikimedia Commons (18× on Linux)

Write as you read, then let go

Most PDF merge tools load every input first, gather them into one document, and write it out at the end. It is a convenient design, but memory grows with the total input. qpdf works this way, and so does the merge code in the lopdf README.

nori reads one input, writes its pages and what they refer to (content streams, fonts, images, annotations) to the output under new object numbers, then drops that input before opening the next. The page tree and the cross-reference table are written last. What is in memory is always one input plus the position of every object written so far.

Load everything, then writememory grows with the total input

  1. load all inputs
  2. gather into one document
  3. write

norimemory is one input

  1. load one
  2. write what its pages need
  3. drop it, next
  • Streams are left aloneFont and image data is written exactly as read, neither decompressed nor recompressed. It is fast, and the output is about the same size as qpdf's.
  • Only what pages needOutlines, forms and the structure tree of tagged PDF are not carried over. Only what can be reached from a page by following references is copied.
  • Parsing can run aheadWith -j 6, six inputs are parsed at once on separate threads. On inputs with many objects this halves the time; memory grows by the inputs being parsed.

Compared with qpdf and lopdf

PDFs picked at random from Wikimedia Commons were copied 10 to 2,000 times and merged with nori, with qpdf, and with the merge code from the lopdf README. All were run as commands on two machines, a Mac (Intel Core i5) and a Linux box (AMD Ryzen 7); the values are the median of 5 runs. The buttons above each chart switch the machine and the input PDF.

Three were chosen from 40 random files for how differently they are built, plus a Japanese government bill from Commons’ Japanese-language category. All are public domain or freely licensed and can be fetched from the links as they are.

  • With few objects per file, both speed and memory differ by orders of magnitudeMerging 2,000 copies of the UK regulation (8,000 pages) took nori 1.12 s and 5.7 MB, qpdf 5.9 s and 423 MB, lopdf 3.6 s and 695 MB on the Mac. On Linux it was nori 0.28 s and 6.0 MB, qpdf 2.4 s and 477 MB, lopdf 1.2 s and 640 MB. nori's memory barely moved from what it used for 10 files (1.8 MB on the Mac, 4.0 MB on Linux).
  • With many objects per file, memory still stays flatThe EU journal has 478 objects per file and takes longer to parse. nori is still 2.9 times faster than qpdf (4.4 on Linux), 4.5 times with parsing run ahead (7.6). At 2,000 files nori used 10 to 16 MB and qpdf 2 to 2.3 GB; lopdf reached 7.4 GB on Linux.
  • With scanned images, the gap in time narrowsThe scanned newspaper has 9 objects per page, so merging is mostly copying image data. For 2,000 files (1.2 GB) nori took 1.53 s and qpdf 2.60 s on the Mac, 1.7 times apart, and 1.37 s against 1.62 s on Linux, 1.2 times. Memory was 5 to 7 MB for nori, 57 to 70 MB for qpdf, and 2.6 GB for lopdf at 2,000 files on Linux (the Mac stopped at 1.3 GB for 1,000).
  • CJK documents behave the sameThe Japanese bill (made with JUST PDF, with MS Mincho subsets embedded, 14 pages) merged 2,000 times (28,000 pages) took nori 1.28 s and 8 MB, qpdf 7.5 s and 686 MB, lopdf 7.5 s and 1.5 GB on the Mac; on Linux nori 0.50 s and 6.6 MB, qpdf 4.2 s and 768 MB, lopdf 3.5 s and 1.4 GB.
  • Both machines show the same pictureEvery tool is faster on the Ryzen 7 Linux box than on the Mac. The gap between nori and qpdf is wider on Linux for PDFs with many objects and narrower for the scanned images. Memory grows the same way on both.
  • lopdf is not slow; the merge code is the problemnori itself parses inputs with lopdf. The README's merge code gathers every input into one Document and saves at the end, so memory grows with the total input. Objects no page refers to stay in the output, which makes it a little larger.

How it was measured

On two machines: a Mac with an Intel Core i5-8500B (6 cores, 16 GB, macOS 15.8) and a Linux box with an AMD Ryzen 7 6800H (8 cores, 16 threads, GEEKOM A6, 32 GB, Omarchy 4.0.6, based on Arch Linux). Both ran nori 0.1.0, qpdf 12.4.2 and lopdf 0.47.0. The input was copied the given number of times, each tool was run as a command once to warm up and then 5 times, and time and peak resident memory were taken from /usr/bin/time. Outputs were checked with qpdf for page count and with --check. The same input PDFs were used on both machines, but the numbers depend on the environment.

nori -o output.pdf input-00001.pdf input-00002.pdf ...
nori -j 6 -o output.pdf input-00001.pdf input-00002.pdf ...

qpdf --warning-exit-0 --empty --pages input-00001.pdf input-00002.pdf ... -- output.pdf

lopdf-merge -o output.pdf input-00001.pdf input-00002.pdf ...

The inputs are PDFs picked at random from Wikimedia Commons; bench/fetch.py builds the list and downloads them. lopdf reached 400 MB to 1.3 GB at 100 files of the journal and 1,000 of the newspaper, so larger counts were not run on this machine. The benchmark script and the list of inputs are in bench/.

What is copied, what is not

Copied

  • Pages, in input order
  • Content streams, resources, fonts, images
  • Annotations (references to pages are redirected to the output pages)
  • MediaBox, CropBox, Resources and Rotate set higher in the page tree (written into each page)

Not carried over

  • Outlines (bookmarks) and AcroForm fields
  • Named destinations, the structure tree of tagged PDF
  • The document information dictionary and XMP metadata
  • References to objects that do not exist (they become null)

Install

Build from source with Rust 1.88 or later. The result is a single nori binary with no dependency on qpdf or other external commands.

cargo install --git https://github.com/champierre/nori
nori --version

Usage

Give the output and the inputs. Pages come out in input order.

One unreadable input fails the whole merge and no output file is left behind. The reason goes to standard error as nori: ....

nori --help lists the options and exit codes.

Command line

# merge three PDFs in order
nori -o merged.pdf a.pdf b.pdf c.pdf

# read the input list from a file (one path per line; - is stdin)
ls pages/*.pdf | nori -o merged.pdf --list -

# parse six inputs at once
nori -j 6 -o merged.pdf --list inputs.txt

From Rails

require "open3"

Dir.mktmpdir do |dir|
  inputs = pdfs.each_with_index.map do |pdf, i|
    File.join(dir, "#{i}.pdf").tap { |path| File.binwrite(path, pdf) }
  end
  output = File.join(dir, "merged.pdf")
  _out, err, status = Open3.capture3("nori", "-o", output, *inputs)
  raise "PDF merge failed: #{err}" unless status.success?
  File.binread(output)
end
